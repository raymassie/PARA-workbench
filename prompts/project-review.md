# Project checks and balances

Use for “Review my projects”, “What information is missing?”, or before/after
substantive authorized project work. The Librarian owns the review and may use PM
for real coordination needs. Do not create a new reviewer agent or mandatory team.
Review the relevant project by default; inspect all active projects only when asked
or needed for an actual linked-project dependency. `prompts/audit.md` remains the
read-only structural/link/schema audit; this review assesses project coherence.

## Check against sources

Read the canonical project note/README, its live task list or designated tracker,
goal, dates and date certainty, selected skills, evidence, decisions, pending review
flag, and relevant linked artifacts. Exclude implementation trees unless a specific
claim needs verification and access is authorized.

- Is the finish line concrete, and do current tasks actually lead to it?
- Are start/end dates confirmed, targets, or explicitly undecided? Is a scheduled
  date inconsistent with dependencies or known capacity? Do not invent a deadline
  or treat an explicit undecided answer as an unanswered question every session.
- Do checked tasks have appropriate evidence? Distinguish user-reported completion,
  accepted output, direct verification, and deployed/delivered results.
- Are there missing acceptance checks, blocked dependencies, stale assumptions,
  contradictory sources, unassigned handoffs, or pending decisions that matter now?
- Does the selected skill plan still fit the actual scope? Is a role unnecessary,
  unavailable, premature, or being mistaken for an already executed agent?
- Have meaningful completed outcomes changed next actions, another linked project,
  or the designated live tracker? Is claimed follow-through actually recorded?

## Ask useful questions

Prioritize up to three material knowledge gaps or decisions. For each, state what
is missing, why it changes the next action, and one concise question. Reuse prior
answers. Proceed with independent authorized work while awaiting blocking answers;
make reversible assumptions explicit. Do not ask the user to supervise routine
verification or repeat a fact available in the provided sources.

## Bounded refresh loop

Complete an action → Update the canonical list → review evidence and dependencies
→ resolve material gaps → choose the next action. Use the task page's existing
Update operation and the project/Home digest workflows; no additional dispatcher
or background agent is required.

“Review my projects” is diagnostic/read-only. “Refresh project status” authorizes
local reconciliation of the relevant project records and generated Home views,
within the existing task scope. It does not authorize delivery, publication,
archiving, spending, or changes to a designated external tracker.

Keep the pending review flag until relevant follow-through is done; record a real
blocker rather than falsely clearing it. Do not ask the same answered question on
each pass. An unchanged refresh should not create new tasks, log entries, or work.
Stop when the requested outcome is met or a specific decision/access blocker
remains. Editorial revisions use the controller's existing bounded loop; do not
turn repeated failures into an unbounded task generator. Completed projects stay
quiet unless explicitly reopened or new scope is accepted.

Optional periodic checks can report stale projects from dated evidence and git
history, without changing status merely because time passed. Existing inactive
report/schedule helpers are optional; installing this workflow activates none.

## Return or reconcile

For a read-only review, return findings and questions inline; change no project,
profile, activity log, or tracker. Do not mark review reconciled merely because
the checklist was read.

During authorized project work, perform necessary in-scope corrections and accepted
follow-up, update the existing canonical notes/task list and Home as appropriate,
and preserve useful history and user decisions. Use the transaction workflow for
bulk edits. Clear a pending review flag only after the relevant work is complete,
or record the specific unresolved gap/blocker. Log only when vault writes are in
scope. Report remaining decisions plainly; do not silently expand goals, spend,
publish, deploy, or archive. A selected specialist is not a completed handoff.
